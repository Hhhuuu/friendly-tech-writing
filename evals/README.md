# Тестирование friendly-tech-writing

Набор проверяет структуру skill, сохранение технических инвариантов и качество на нескольких типах документов. Он не сравнивает ответы посимвольно: допустимы разные хорошие формулировки.

## Быстрая проверка без обращения к модели

```bash
python3 evals/run_evals.py validate
python3 -m unittest discover -s evals -p 'test_*.py'
```

Эти команды проверяют расположение skill, frontmatter, ссылки на references, fixtures, описание сценариев и сам механизм проверки результатов.

## Поведенческий прогон

Один сценарий:

```bash
python3 evals/run_evals.py run --case rewrite-readme
```

Все сценарии:

```bash
python3 evals/run_evals.py run
```

Для проверки устойчивости запусти каждый сценарий несколько раз:

```bash
python3 evals/run_evals.py run --runs 3
```

Команда запускает `codex exec` в режиме `read-only`. Ответы сохраняются в `evals/output/`, который исключён из Git. После изменения правил уже сохранённые ответы можно проверить повторно:

```bash
python3 evals/run_evals.py check
```

Флаг `--model` фиксирует модель для сравнимых регрессионных прогонов:

```bash
python3 evals/run_evals.py run --model gpt-6.1-sol --runs 3
```

Детерминированные проверки ловят потерю команд, версий, имён контрактов, предупреждений и характерные нежелательные фразы. Критерии из поля `rubric` требуют человеческой или независимой агентской оценки: скрипт намеренно не пытается свести качество текста к регулярным выражениям.

## Проверка активации

Положительные и отрицательные запросы находятся в `evals/trigger-cases.json`. Их нужно запускать без явного `$friendly-tech-writing` и проверять, выбирает ли Codex skill по `description`. Этот слой оставлен ручным, потому что текст ответа не доказывает факт активации, а формат внутренних событий может меняться.
