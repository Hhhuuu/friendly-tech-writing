# Примеры редакторских решений

Примеры показывают направление, а не фразы для обязательного копирования.

## Начать с сути

Неудачно:

> В современном мире информационных технологий эффективное управление конфигурацией играет важную роль. В данном документе мы рассмотрим основные аспекты настройки сервиса.

Лучше:

> Этот документ поможет настроить сервис для локальной разработки. После настройки приложение будет принимать запросы на `http://localhost:8080`.

Почему: читатель сразу видит назначение и проверяемый результат.

## Заменить декоративную структуру логикой

Неудачно:

> **Гибкость:** система поддерживает разные сценарии.
>
> **Надёжность:** система обеспечивает стабильную работу.
>
> **Масштабируемость:** решение легко масштабируется.

Лучше:

> Сервис можно развернуть в одном экземпляре для разработки или в нескольких экземплярах за балансировщиком. Состояние хранится в PostgreSQL, поэтому перезапуск экземпляра не приводит к потере заданий. Предел горизонтального масштабирования пока не измеряли.

Почему: вместо абстрактных достоинств появились механизм, границы и честная неопределённость.

## Не превращать повествование в список

Неудачно:

> Процесс включает:
>
> - разработчик создаёт ветку;
> - разработчик вносит изменения;
> - затем проводится проверка;
> - после этого изменения объединяются.

Лучше:

> Разработчик создаёт ветку и открывает pull request с изменениями. После автоматических проверок и ревью pull request можно объединить с основной веткой.

Почему: это короткая связная последовательность, для которой отдельные пункты не помогают ориентироваться.

## Ставить условие перед действием

Неудачно:

> Удалите старый индекс. Этот шаг нужен только при переходе с версии 2.x.

Лучше:

> Если вы переходите с версии 2.x, удалите старый индекс. При обновлении с версии 3.x пропустите этот шаг.

Почему: читатель узнаёт область применимости до потенциально разрушительного действия.

## Не маскировать неизвестное

Неудачно:

> Новая схема значительно повысит производительность и обеспечит бесперебойную работу системы.

Лучше:

> Новая схема убирает один запрос к базе данных из операции чтения. Влияние на задержку под рабочей нагрузкой ещё не измеряли. Отказоустойчивость этим изменением не меняется.

Почему: текст отделяет известный механизм от неподтверждённого эффекта.

## Дружелюбно сообщать об ошибке

Неудачно:

> Неверный запрос. Пользователь должен корректно заполнить обязательные поля.

Лучше:

> Не удалось создать проект: поле `name` пустое. Укажите название и повторите запрос.

Почему: сообщение называет результат, причину и следующее действие без обвинения читателя.

## Сохранять отрицательные последствия решения

Неудачно:

> Мы выбрали Kafka, поскольку это современное, надёжное и масштабируемое решение.

Лучше:

> Мы выбрали Kafka, потому что потребителям нужен повторный просмотр событий, а ожидаемый поток превышает возможности текущей очереди. Решение добавляет отдельный кластер, мониторинг лагов и новую компетенцию для дежурной команды.

Почему: обоснование связано с требованиями и показывает эксплуатационную цену.

## Сокращать метатекст

Неудачно:

> В следующем разделе мы подробно рассмотрим процесс настройки аутентификации и расскажем о шагах, которые необходимо выполнить.

Лучше:

> Для аутентификации создайте сервисный аккаунт и передайте его идентификатор в `SERVICE_ACCOUNT_ID`.

Почему: текст говорит о предмете, а не анонсирует собственную структуру.

## Не удалять полезный список

Неудачно:

> Для запуска нужны Docker версии 27 или новее, 4 ГБ свободной памяти и доступ к реестру `registry.example.com`.

Лучше для страницы установки:

> Перед запуском подготовьте:
>
> - Docker 27 или новее;
> - 4 ГБ свободной памяти;
> - доступ к `registry.example.com`.

Почему: независимые требования удобно проверить по одному. Цель стандарта — не запретить списки, а использовать их осмысленно.
